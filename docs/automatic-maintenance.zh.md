# 自动记忆维护

默认 `reflectionMode: notify`，待办保存在状态台账中，可通过 `memory_stats` 和 `memory_maintain` 查询。`reflectionMode: auto` 使用固定整理会话，按保存的进度分批整理。每个父对话最多两个维护身份，分别负责核对与整理。任务收尾核对与存量维护共用空间级派发窗口，结果保存在内部记录中。

主模型在任务中使用基础工具查阅和更新笔记。后台根据本轮证据照看相关笔记的遗漏、矛盾和重复；没有需要改动的内容时正常结束。

## 任务收尾检查

`turnReviewEnabled: true` 默认启用任务收尾核对。插件在真实用户任务正常完成后积累成功工具证据的指纹与来源引用，根据宿主 `message.isError` 和进程退出码排除失败调用。默认积累至少 6 条未处理的新证据作为一个批次，一个已完成用户回合也可满足；证据窗口最多保存 32 条，数量不足时继续跨回合积累。

重复返回内容会去重，主任务通过 `evidence_call_ids` 或当前会话 `sourceSeqs` 成功保存的证据会从待核对集合剔除。只有当前回合带来新证据、门槛和冷却均满足时，才恢复固定核对会话，传入有界任务摘要与成功事件引用。核对者可以分页补读分配给当前运行的父来源，先完整读取相关记忆，再判断是否更新或保存新知识。成功写入后立即保存进度，并消费该写入明确绑定的父证据；完整结束后消费其余已核对证据。失败、超时或延期只保留未完成部分，实际派发仍计入冷却。未完成核对在有新证据且共享冷却到期后续跑，不必重新凑满首次派发的数量门槛。

实际写入由程序记账并立即保存，维护代理通常只需调用 `memory_maintenance_complete({summary})` 结案，不必重报 `changed` 或完整待办清单。所有业务校验在结束代理之前执行；错误包含具体条目及修正动作，代理可补读或改正后重新提交。程序根据真实写入规范化条目状态，已有写入不会因模型填成 `retained` 丢失；上轮的 `changed` 若本轮仅完整读取，则按保留记录。插件等待成功工具回执、正常回合结束及会话持久化后记录完成状态；PTC 内部调用还需等待外层调用成功。结果保存到 `maintenance-runs.json`，主会话保留用户任务的回答。无变化记录为 `unchanged`。纯闲聊、插件发起的轮次和仅调用记忆工具不会增加业务证据。

执行记录按父会话与完成事件去重，同一用户回合最多派发一次自动维护。事实来源指向父会话的验证事件，核对者身份单独记录。收尾核对沿用维护调用、写入、输出和超时预算，使用父会话的模型路由；`turnReviewReasoningEffort` 非空时单独指定核对思考档，否则沿用父会话。存量整理默认同样沿用父会话当前的模型。每次实际核对会消耗模型调用，`turnReviewEnabled: false` 可关闭。

收尾核对与批整理统一读取当前空间 `maintenance-runs.json` 中最近一次真实派发时间，默认间隔至少 30 分钟。冷却期间继续积累证据，插件重装和会话切换沿用同一份台账。冷却到期本身不会唤醒任务，仍需后续有效回合结束。

## 配置

```yaml
- id: dsh-layered-memory
  config:
    turnReviewEnabled: true
    turnReviewMinEvidence: 6
    reflectionEnabled: true
    reflectionMode: auto
    # 可选覆盖项：两项都不填即跟随当前对话模型，需要钉到指定模型时再成对填写
    # maintenanceLlmProvider: opencode-go
    # maintenanceModel: deepseek-v4.1-flash
    maintenanceReasoningEffort: ''
    turnReviewReasoningEffort: ''
    maintenanceMaxTokens: 16384
    maintenanceCooldownMinutes: 30
    maintenanceMaxCalls: 64
    maintenanceMaxWrites: 6
    maintenanceTimeoutSeconds: 300
    # 索引整理水位线：目标字符 = l1MaxChars × indexTargetRatio（默认 0.9）
    indexTargetRatio: 0.9
```

存量整理的 LLM 提供方与模型是可选覆盖项：两项都填写才会覆盖路由；只填一项会在加载时报错；都不填则沿用父会话当前模型。上面注释里的 OpenCode Go 的 DeepSeek V4.1 Flash 是一个覆盖示例。核对每次显式读取父会话当前的模型配置。旧 `maintenanceProvider` 配置移除，执行统一使用公开 Agent 接口。

`maintenanceMaxTokens` 是每次模型响应的输出上限，一轮维护可以包含多次响应。`maintenanceMaxCalls` 统计工作工具调用，检查点和完成工具另行计数；`maintenanceMaxWrites` 统计实际产生变化的写入操作，状态栏则按发生变化的条目去重。`maintenanceTimeoutSeconds` 是整轮时限，到期会结束本轮并保留已保存的进度。

`indexTargetRatio` 控制索引整理的目标水位线，默认 0.9，可设 0.5 至 1：整理目标字符 = `l1MaxChars` × `indexTargetRatio`。`l1MaxChars` 是注入预算的硬上限，不是整理目标；不允许靠调高 `l1MaxChars` 回避整理，提高到预算上限不是解法，整理必须自己把索引压到水位线以下，为后续写入留出空间。

上述预算是当前默认值。存量 profile 若显式填写了 `maintenanceMaxTokens: 4096` 或 `maintenanceMaxCalls: 32`，升级后仍会使用原值；需要提高预算时，修改对应配置，或移除该项以使用新默认值。

`maintenanceCooldownMinutes` 统一控制两条自动维护路径。已有配置中的 `turnReviewCooldownMinutes` 改为该项。

## 何时检查

程序扫描按 `maintainEveryTurns` 与 `reflectCooldownTurns` 节流。索引高于水位线时（目标字符 = `l1MaxChars` × `indexTargetRatio`，默认 0.9）创建语义审阅作业，保存来源会话与触发事件；扫描已有待办保持原归属。模型先浏览完整标题目录、选择候选，再读取正文判断；候选数按缺口动态放大，索引超出水位线越多，本轮选取的候选越多，不再固定 8 个。确定的重复、同名冲突和 pending 也会形成待办。冷条目仅提供复核线索。

省索引空间的主力手段是合并同主题条目：把 N 条同主题条目合并成 1 条，省下 N-1 条的名字开销。归档失效条目是次要手段，只在条目确实失效或被替代时使用；也不能为了压索引删除有效知识。模型读过后认为应保留的条目可以按保留结案，但不能因为已审过几条就收工：一轮审完若索引仍高于水位线且本轮有真实改动，作业继续派下一轮，直到压到水位线以下，或一整轮没有任何改动才停。整轮零改动后回落到日常变更门槛，等日常任务新增或实质修改的不同条目累计满 20 条再安排下一轮。收尾核对与批整理自身的写入均不计入该累计。

主模型通过 `memory_review({entry,reason})` 登记明确的新旧证据冲突。插件自动绑定当前回合未保存的成功验证事件，过滤失败、控制和记忆工具调用，去重后取最近最多四条；回执中的 `sources` 返回真实 `sourceSession` 与 `sourceSeqs`。也可显式传入 `evidence_call_ids` 指定成功证据。插件保存脱敏片段与精确引用，维护会话据此复核。待办可越过普通扫描轮次门槛，自动执行仍受 `maintenanceCooldownMinutes` 限制。

`autoPending: false` 为默认值。启用后，同一工具先失败后成功的序列进入候选，正式记忆仍需提交精炼正文和验证证据。候选可以显式丢弃，结果留在管理历史中。

## 子任务权限与完整读取

基础 `memory_search/list/read/write/update` 随会话提供，`memory_activate` 的 `common` 和 `manage` 模式只补充工具。读写权限由用户配置 `memoryAccess`、`subagentMemoryAccess` 决定，普通子代理默认只读。模型不能通过激活参数设置持久权限；历史激活也只恢复工具模式。

DSH 0.2.1-rc.2 起，插件通过公开 `agents.create/resume` 创建或恢复固定会话，在发布前的 setup 中为当前运行安装模型选择、请求输出上限和工具边界。身份保存在公开存储域中，与 namespace、cwd、memoryDir 分开，重装和重启后继续使用原 ID。空闲时释放运行资源，长期历史由宿主的正常请求生命周期原生压缩并保留会话身份。恢复旧核对会话时，先应用当前父会话模型选择；历史 provider 不再通过插件额外的压缩预检阻断新请求。

新的维护会话从独立上下文开始，后续使用增量工作包。每次运行给出独立 runId、前次结果、失败原因、仍然有效的已保存条目及剩余任务，避免把旧对话中的成果误认成本轮操作。读取资格按本次运行建立，普通子代理默认 `read` 访问。

修改已有条目前必须完整读取同一 revision。类型、空间和 key 共同构成身份，同版本分页范围会累计，真正读全后取得资格；单独读取尾页或另一种类型不算完整。自己的完整写入也取得新版本资格，无需为连续整理重复读取。实际更新在写锁内检查该条目版本，同空间无关条目的修改不再中止整个维护。归档还需给出明确的替代条目。新建条目可直接通过 `memory_write` 创建。

维护代理先保存选中的候选，成功写入自动记录并推进对应候选；没有修改的条目可用 `memory_maintenance_checkpoint` 保存保留或待证据判断。核对和整理均提供该工具。保留条目须已完整读取，未读完可以说明缺口并等待证据。工具回执提供剩余调用、写入、时间及已保存进度。检查点与完成工具不占工作调用额度；工作或写入额度耗尽会返回收尾指引而非立即取消代理，仍可提交 `status: deferred`。超时或取消也保留已保存进度；来源会话有新的有效工作且共享冷却到期后再续跑。零进度超时和证据不足的事项等待新证据或显式维护请求。相似度用于选择线索，合并时保留来源和适用条件。

维护锁、写锁和核对认领都记录持有进程。宿主异常退出后，同机新进程自动回收死亡进程的锁并接续已保存进度。活进程持有的锁继续互斥；重启恢复时，中断的旧运行记录显示为延期，保留实际写入与剩余任务。

`memory_maintain({namespace, review:true})` 可显式认领存量待办并启动语义审阅。手动请求可以越过自动冷却，仍遵守空间忙锁、调用、写入与时间预算；实际派发也会刷新后续自动维护窗口。旧版留下的无归属待办可通过该入口继续处理。

## 状态组件

“记忆状态”组件作为独立子包 `@dsh-external/dsh-layered-memory-status` 随主包交付，可在插件管理页独立启停，挂载在宿主的 `conversation.composer.dock` 槽位。后端通过父会话限定的快照与增量流传递当前阶段、真实变更和运行记录。点击展开插件详情浮层，可以查看两个固定维护会话的只读历史并停止正在执行的任务。

运行时显示轻微活动动效，完成后展示真实变更数或核对完成状态，等待证据单独标记。计数按实际变更条目标识去重。上次核对未完成时保留具体原因。状态行按实际内容占宽，尚无运行记录时显示可点击的待命入口，窄窗口单行省略；详情浮层独立布局，主对话阅读位置保持稳定。会话切换释放旧订阅并淘汰缓存。

迁移根据真实维护记录接管已有插件会话。过去的原生菜单历史项保留，新任务持续复用已登记身份；固定维护的当前状态和控制统一由插件组件提供。

## 结果与成本

`turn-review-state.json` 按父会话与命名空间保存有界证据窗口、已处理指纹和派发认领，工具返回正文保留在原会话中。派发时间统一保存在 `maintenance-runs.json` 中。

`memory_stats` 提供当前空间、最近维护状态与审阅台账。`review-state.json` 保存语义审阅作业的来源会话、触发事件、条目版本、结果理由及日常变更累计；`reflection-state.json` 保存程序扫描状态及待办身份变化，无关记忆改写保持同一待办的变更标识；`maintenance-runs.json` 保存最近 50 次执行的父会话、回合身份、模型路由、总调用数与工作调用数、真实写入及其来源、剩余条目、最近错误和可取得的 usage。

固定会话的只读历史展示维护回复、工具调用与实际错误。usage 来自本次运行的宿主记录，缺失时保留未知值，不根据调用次数估算费用。单次维护的消耗按本次事件边界核算，固定会话的历史累计值与它分别展示。

## 真实验收

在官方原版宿主的隔离 profile 中使用一段真实旧长会话的副本，保留记忆、待办和自动维护配置，连续完成实际任务。按父会话、用户回合和 purpose 对照维护台账，观察派发、完整读取、修改、检查点及资源释放。重复执行、切空间和重启后，两个固定身份保持相同，维护 run 与预算逐次独立。

覆盖单个已完成任务积累足够证据、连续多轮任务及真实 30 分钟冷却边界。分别观察主模型写入与后台核对结果，包括正常的零变更。核对两条路径共享派发时间、同一回合去重、已保存证据消费，以及维护自身写入的归属。遇到模型错误或部分完成超时，单列结果并观察后续恢复。结束后恢复临时模型选择，归档本次产物，保留会话和维护台账。
